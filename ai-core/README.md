# 检测模块

由 Spring Boot 调用的本地推理模块，负责目标检测、轨道区域估计、视频抽帧、预警目标关联和可选的图像理解建议。

## 源码职责

| 文件 | 职责 |
| --- | --- |
| worker.py | 常驻进程协议、模型缓存、读取任务、检测、输出进度和结果 |
| geometry.py | 轨道几何估计、侵入判定、抽帧索引和目标关联 |
| vision_advice.py | 关键帧选择、DeepSeek 请求、系统提示词、JSON 解析和本地规则回退 |
| prepare_model.py | 将业务目标类别嵌入 YOLO-World 权重 |
| benchmark.py | 使用相同常驻运行时测量真实视频吞吐，保存各轮证据与汇总 |
| catalog.example.json | 可选模型的标识、名称、描述和类别示例 |
| evaluate.py | 使用人工标注的图片评估类别匹配和定位质量 |
| tests/ | 危险区几何、侵入判定和抽帧测试 |
| train/ | YOLO-World 训练、微调、续训与评估入口，详见 [训练说明](train/README.md) |
| datasets/ | 自备图片与 YOLO 标注的目录模板，详见 [数据格式](datasets/README.md) |

## 环境与模型

在安装了匹配硬件的 PyTorch 的 Python 环境中执行：

```powershell
python -m pip install -r .\ai-core\requirements.txt
```

从仓库根目录运行模型准备命令，输入和输出由用户指定：

```powershell
python .\ai-core\prepare_model.py `
  --source 'C:\TrackGuardAssets\yolov8l-worldv2.pt' `
  --output 'C:\TrackGuardAssets\trackguard-world.pt'
```

模型准备首次可能下载文本编码权重，已有输出不会被覆盖。正式检测使用已保存的类别特征，不在请求中重新编码文本。多模型配置方式见 [项目 README](../README.md)。

业务类别包括人员、车辆、摩托车、动物和岩石 / 障碍物，与 SynRailObs 的五类训练标签对应。摩托车独立分类；岩石事件显示“岩石”，内部继续使用 `obstacle` 标识兼容历史数据。轨道定制模型原有的倒木、较大纸箱和行李箱仍归入障碍物；通用模型支持的范围取决于其内嵌类别，界面提供类别选项不代表模型权重已完成微调。历史预警不重新分类。

## 轨道危险区如何识别

自动模式缩小图片后进行灰度化、高斯平滑、Canny 边缘检测和霍夫直线检测。程序先按长度、位置与汇聚关系选择两条候选钢轨并生成四边形；直线证据不足时，再按多个水平带跟踪左右边缘并拟合二次曲线，生成多点危险区。视频的单个后续帧无法定位时复用首帧的有效区域。首帧没有足够证据时要求手动标定。

目标底部中心位于区域内，或底部 12% 高度的接触带采样点有至少 20% 位于区域内时判为侵入。该方法同时支持直线四边形和弯道多边形。视频通过类别和检测框交叠进行关联，减少连续帧重复计数。

## 耗时与限制

后端按需以 `worker.py --serve` 启动一个常驻进程。标准输入/输出用于私有 JSON 行协议，标准错误输出保存初始化日志；每次任务的结果、进度和截图仍写入各自目录。无需开放 Python HTTP 端口。

工作进程在首个任务到达时导入依赖并加载所选模型，不执行额外的空白预测。模型按权重路径、大小和文件时间缓存，最多保留最近使用的两个模型。每个任务重新设置类别过滤和跟踪状态，避免沿用上一任务的选项或目标计数。

控制线程接收取消信号，在解码、逐帧推理和保存结果的边界检查。正常取消保留模型缓存；卡住、超时或异常状态由 Java 结束进程并在下次任务自动重建。父进程关闭通信管道时 Python 立即退出，避免留下占用显存的后台进程。

默认 CUDA 使用 FP16、最多 8 帧一批、640 输入长边；CPU 使用 FP32 和单帧推理。原始批次还受 64 MB 内存预算限制，大分辨率输入会缩小批量。`sampleSeconds=0` 顺序检查全部帧；0.5–5 秒按间隔抽帧，单任务最多 14400 帧。批量结果按源帧顺序逐一做危险区判断和目标关联，自动轨道定位仍逐帧计算。

只编码并保存总览图和目标关联所采用的证据图；更新证据后清理不再引用的生成图，最终每条记录的截图仍然存在。进度最多约每 250 ms 写入一次，最后一个批次强制更新。每次任务结束时清理模型预测器保留的输入批次。

自动区域计算使用最多 4 个线程，与 GPU 批量推理重叠；结果仍按帧顺序处理。`regionMs` 是区域准备与等待时间，`regionComputeMs` 是并行线程的累计计算时间，后者不参与总耗时求和。实际吞吐受硬件、输入分辨率、模型和轨道画面影响，应使用 `benchmark.py` 在部署环境中测量。

任务结果分别记录工作进程启动、模型加载与指纹、轨道定位、解码、推理、目标关联、标注、截图、进度和通信校验时间。`postprocessMs` 保留为目标关联、标注与截图三项之和，供旧客户端兼容。模型已缓存时，后续任务的模型加载时间为 0。

`performance.inferenceFps` 包括模型预处理、推理、NMS 和结果回传 CPU；`pipelineFps` 额外包括解码、轨道定位、目标关联和证据写入，排除初始化。Java 增加的 `taskFps` 使用任务处理耗时，包含等待引擎与结果校验。所有 FPS 都按实际处理帧数计算。

`worker.py --request <request.json> --output <目录>` 的单次命令方式和 `evaluate.py` 可独立运行，不复用 Spring Boot 管理的常驻进程。

检测结束后，`vision_advice.py` 从工作进程环境读取 `DEEPSEEK_*` 配置。API 地址可填写官方基础地址或完整的 `/chat/completions` 地址。图片与视频均为每个任务最多调用一次；视频携带完整目标关联结果，并只选择类别、风险或时间阶段发生变化的少量证据帧。API Key 不写入请求文件、结果文件或数据库。接口未配置、超时或返回无效 JSON 时，检测仍然成功并保留本地规则建议。

轨道定位采用直线与平滑曲线几何估计；道岔、急弯和遮挡应使用多点人工标定。该算法不是轨道语义分割模型。模型尚未进行铁路专用数据集微调，快速运动和遮挡可能导致漏检或重复计数。
